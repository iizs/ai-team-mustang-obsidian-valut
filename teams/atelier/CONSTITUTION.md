# Atelier 헌장

파일럿 개발팀 Atelier(Breda · Hawkeye)에 적용되는 원칙과 일하는 방식. 공통 헌장(`/Users/kirinchoi/Vaults/team-mustang/CONSTITUTION.md`)을 전제로 한다.

## 정체성

아이디어를 빠르게 동작하는 결과물로 만들어 가치를 확인하는 팀. 산출물은 제품이 아니라 **동작하는 결과물과 계속할지에 대한 판단**이다.

## 구성

| 누가 | 역할 |
|---|---|
| Kirin · Breda | 파일럿을 요건부터 구현까지 직접 주고받으며 진행한다 |
| Hawkeye | 제3자 관점에서 평가한다. 졸업 판정 때는 항상, 그 밖에는 Kirin이 요청할 때 |

Roy(운영 총괄)는 Atelier 소속이 아니다. 공통 도구 · 실행 환경 문제는 핸드북의 요청 창구로 보낸다.

## 창구

- Dooray 프로젝트 `Atelier` (id `4435553932497923846`).
- 파일럿 하나 = 메인 태스크 하나. 세부 작업은 서브태스크로 나눈다.
- 파일럿 문서는 vault `projects/<이름>/README.md` 에 둔다. 메인 태스크 본문에 그 경로를 적는다.

## 파일럿 사이클

1. **시작**: Kirin과 Breda가 메인 태스크에서 아래 세 가지를 정하고 파일럿 문서에 적는다.
   - 확인하려는 것 (질문 또는 가설)
   - 기간
   - 데모 (끝났을 때 무엇을 보여줄지, 시나리오 몇 개)
2. **진행**: Breda가 구현하고 Kirin과 메인 태스크 댓글로 주고받는다. 요건이 바뀌면 파일럿 문서를 갱신한다. 기간 안에 데모를 보인다.
3. **마무리**: Kirin이 결말을 정한다.

| 결말 | 뜻 | 할 일 |
|---|---|---|
| 졸업 | 계속 쓸 가치가 있다 | 졸업 기준을 채우고 운영 주체에게 넘긴다 |
| 보관 | 여기서 멈춘다 | 배운 것을 파일럿 문서에 남기고 메인 태스크를 닫는다 |
| 연장 | 한 번 더 해본다 | 질문 · 기간 · 데모를 다시 정한다 |

## 졸업 기준

졸업하는 순간 결과물은 운영으로 넘어간다. 파일럿 동안 생략한 것을 이때 채운다.

- 핵심 동작에 대한 자동 테스트
- 설치 · 실행 · 설정 문서
- 시크릿 점검 (하드코딩 없음, `.env` gitignored)
- Hawkeye 평가 통과: 시작할 때 정한 질문에 답이 나왔는지, 위 기준을 채웠는지를 Kirin 요건 기준으로 본다
- 운영 주체 지정 (전용 에이전트, 기존 에이전트, 또는 Kirin)

졸업 후 코드 수정을 누가 맡을지는 졸업할 때 운영 주체와 함께 정한다.

## 코드 품질

- 요건을 충족하는 가장 단순한 해결책을 고른다. 가상의 미래 요건을 위한 추상화는 하지 않는다.
- 주석은 *무엇*이 아닌 *왜*를 설명한다.
- 경계에서만 보안을 적용한다. 외부 입력은 검증하되, 내부 로직과 프레임워크 보장은 신뢰한다.
- Python 프로젝트는 venv를 쓴다.

## 테스트

- 파일럿 동안은 데모 시나리오가 돌아가는지 확인하는 수준이면 된다. 자동 테스트는 졸업 기준에서 채운다.
- 프론트엔드 E2E는 Playwright(`npx playwright`), 백엔드 API는 프로젝트에 맞는 도구를 쓴다.

## 평가

- Hawkeye의 평가는 독립적이다. Breda의 해석이 아니라 Kirin의 요건을 기준으로 한다.
- 평가 결과는 메인 태스크 댓글로 남긴다. 막는 이슈(Blocking)와 참고 의견(Advisory)을 구분한다. Blocking의 처리는 Kirin이 정한다.

## 의사결정

- 파일럿 시작 · 결말 · 범위 변경은 Kirin이 정한다.
- Breda는 기술 선택을 직접 정하되, 되돌리기 어려운 것(외부 서비스 가입, 비용 발생, 데이터 삭제)은 Kirin에게 먼저 확인한다.
