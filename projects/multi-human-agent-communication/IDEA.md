# multi-human-agent-communication

여러 명의 사람과 여러 에이전트가 함께 일하는 환경 및 커뮤니케이션 구조에 대한 아이디에이션.

---

## 브레인스토밍 메모 (2026-04-21)

### 협업 구조의 발전 단계

| 단계 | 구조 | 상태 |
|------|------|------|
| 1단계 | 사람 1 : 에이전트 1 | ✅ 구축 완료 |
| 2단계 | 사람 1 : 에이전트 n | ✅ 우리 팀이 증명 중 |
| 3단계 | **사람 n : 에이전트 m** | 🔍 현재 탐색 중 |

---

### n:m 협업의 두 가지 구조

#### n:m - Flat Mesh
모든 사람과 에이전트가 대등하게 연결된 구조.
```
사람1 ─ 에이전트1
사람2 ─ 에이전트2  ← 모두 동등하게 연결
사람3 ─ 에이전트3
```

#### n:m - Clustered
각 사람이 자신의 에이전트 클러스터를 가지고, 클러스터 단위로 연결되는 구조.
```
{ 사람1, 에이전트1, 에이전트2 }
{ 사람2, 에이전트3 }              ← 클러스터 간 연결
{ 사람3, 에이전트4 }
```
- 에이전트는 특정 사람의 의도를 대리 → 사람이 클러스터의 중심
- 책임 소재가 명확함
- 현재 우리 팀도 이 구조 (Kirin + Falman/Roy/Breda/Hawkeye)

---

### 핵심 제약: 현 세대 AI는 텍스트 기반

- LLM은 텍스트로 소통 → 에이전트가 맥락을 얻으려면 반드시 텍스트가 필요
- **문서 기반 협업이 베스트 프랙티스일 수밖에 없는 이유**
- 업무 산출물로서의 문서화는 필수이며, AI 도입이 이를 자연스럽게 강화함

---

### 사람 n 명으로 확장 시 생기는 문제

**1. 소통 수단 강제 문제**
- 1:n 구조에서는 텍스트 기반 소통이 큰 걸림돌이 아님
- 사람이 여럿이 되면 "왜 대화/영상통화 대신 메신저를 강제당하는가" 불편함 발생
- 사람 간 자연스러운 소통(대화, 영상통화)과 AI 요구(텍스트) 사이의 충돌

**2. 실시간 에이전트 반응 트리거 문제**
- 텍스트 채널에서는 @멘션이 명확한 트리거
- 음성/영상 회의에서는 동등한 트리거 수단이 없음
  - 이름 호출("팔만아") → 의도 vs 단순 언급 구분 어려움, STT 오인식 등
- 현재 우리 팀: 모든 채널 메시지를 흡수하되, @멘션 없으면 응답 안 함

---

### n:m - Clustered 구조의 해결 방향

**핵심 원칙: 대화는 사람이 주도, 에이전트는 후처리로 맥락 흡수**

```
[회의/대화] 사람들끼리 자유롭게 (음성, 영상통화 가능)
      ↓ STT + 요약
[문서화] 회의록, 결정사항 텍스트화
      ↓ 각 클러스터 에이전트가 흡수
[실행] 에이전트가 자기 사람에게 필요한 액션 제안/처리
```

- 사람은 자신이 편한 방식으로 소통 (텍스트 강제 없음)
- 에이전트는 실시간 반응 대신 회의 산출물을 통해 맥락 파악
- 클러스터 간 에이전트 조율도 문서를 통해 → 구조 일관성 유지

### 비동기 협업 구조 — 에이전트를 팀의 일원으로

에이전트가 실시간 반응 없이도 팀에 참여하는 방식: **비동기 태스크 시스템 활용**

비동기 협업 도구: GitHub Issues, Jira, Linear, 두레이, Notion DB 등

**에이전트의 역할:**
- 할당된 태스크 처리
- 완료 후 다음 사람/에이전트에게 재할당
- 필요시 새 태스크 생성

```
사람A가 이슈 생성 → 에이전트1 할당
  → 에이전트1 처리 후 사람B에게 재할당 (검토 요청)
  → 사람B 승인 후 에이전트2 할당 (다음 단계)
  → 에이전트2 완료 후 이슈 닫기
```

(사례: Envy WORKFLOW.md — 번역/SNS 업로드 파이프라인)

---

### 태스크 정의 방식의 두 극단

| 방식 | 예시 | 장점 | 단점 |
|------|------|------|------|
| **자연어형** | 본문에 프롬프트/지시 직접 기술 | 유연, 어떤 일이든 가능 | 가독성 저하 |
| **레이블형** | `task:translate-post` 레이블 | 명확, 가독성 좋음 | 사전 정의된 유형만 가능 |

- 사람-사람 협업에서도 동일 패턴 존재 (루틴 태스크 → 레이블/템플릿, 신규 태스크 → 자연어 기술)
- 에이전트 협업 설계도 이 두 방식의 조합으로 접근 가능

### 에이전트 트리거 방식 비교

**웹훅 방식**
- 이벤트 발생 즉시 트리거 → 실시간에 가까움
- 각 팀원이 웹훅 엔드포인트를 로컬에 띄워야 함
- 기업 수준에서 확장 어려움 (네트워크 환경 다양)

**폴링 방식 (기업 환경에 적합)**
- 에이전트가 주기적으로 "내 할 일 있나?" 체크
- 인프라 의존 없이 각자 로컬에서 독립 동작
- Claude Code에서는 **폴링 MCP**로 구현 가능

**폴링 MCP 구조:**
```
MCP 폴링 (N분마다, LLM 사용 없음)
  → GitHub/두레이 API 조회 (HTTP 호출만)
  → 할당된 이슈 발견 시 Claude Code 세션에 전달
  → 여기서부터 LLM 개입 (이슈 읽고, 판단하고, 실행)
  → 없으면 다음 폴링까지 대기 (LLM 비용 0)
```

- 대기 시간엔 LLM 비용 없음 → 비용 효율적
- openclaw에서 30분 폴링으로 검증된 패턴
