## INGEST (큰 source 처리)

### 27KB markdown ingest
- read_source 1회, read_page 6회, write_page 1회, patch_page 8회, iters=10 tool_calls=15+
- **8개 페이지** 생성 + 기존 페이지 보강 (read_page → patch_page 조합으로 활용)
- Anthropic Sonnet이 자율적으로 "분석 → 계획 → 행동 → 반복" 패턴 수행

### 발견된 이슈 (모두 핫픽스로 흡수)

| 이슈 | 원인 | 핫픽스 |
|------|------|--------|
| `max_tokens` 한도(4096 default)로 단일 페이지 생성 실패 | 하드코딩 4096 너무 작음 | `LLM_MAX_OUTPUT_TOKENS` env (8192 default, 64k까지) |
| tier 1 30k TPM 한도 도달 | agentic loop 누적 input | Anthropic prompt caching 적용 → cache_read 22k+ 누적, fresh input 1.5-5k |
| 429 발생 시 SDK 3회 retry 후 fail | retry 부족 | max_retries=5 + app-level RateLimitError retry 1회 (Retry-After 존중) |
| Jobs Steps에 1개 step만 표시 (실제 15개 tool 호출) | SQLAlchemy JSON `flag_modified` 누락 | `_persist_steps`에 `flag_modified` 추가 |
| `created` 필드에 LLM hallucinate (2026-03-18 등) | LLM 신뢰 + 시스템 강제 부재 | 신규 페이지 `created = now` 강제, 기존 페이지 보존 |
| 새 노트북 셋업 시 greenlet 누락 | requirements.txt에 명시 안 됨 | `sqlalchemy[asyncio]` extras로 변경 |
| **Single LLM call이 단일 호출만으로 TPM 한도 초과** (input 34k) | 새 job의 read_source 결과가 큰 markdown | Tier upgrade 또는 future cache_control on tool_result. 지금은 retry로 흡수. |

### 캐싱 관찰 (prompt caching 적용 후)

```
Call 1: input=424   cache_create=1901  cache_read=0      ← 첫 호출, system+tools 캐시 생성
Call 2: input=17690 cache_create=441   cache_read=1901   ← 큰 tool_result fresh
Call 3: input=17791 cache_create=441   cache_read=1901   ← 동일 fresh 다시
Call 4: input=2287  cache_create=17653 cache_read=2405   ← 이제 큰 content 캐싱
Call 5: input=5728                     cache_read=20095  ← 큰 content가 cache hit
Call 6: input=4749                     cache_read=22293
Call 7: input=1509                     cache_read=22344
```

### 5번 — rename 시나리오 이슈

문제: rename 후 기존에 [[old]] 참조하던 페이지들이 갱신 안 됨 → `[[old]]` 링크가 dangling 상태로 SC-39 안내 페이지로 노출.

**진단**:
- LLM이 `get_backlinks(old)` 호출 → backlinks 인덱스 조회
- 일부 페이지의 backlinks 인덱스가 **누락 상태** (v0.3.1 이전 페이지 또는 갱신 hook 누락 케이스)
- → LLM이 영향 범위 인지 못 함 → 갱신 안 함

**해결**:
1. **즉시 회복**: `init_backlinks.py --rebuild-backlinks` 실행 → 위키 전체 스캔으로 backlinks 재구축 (Kirin 적용, 즉시 해소)
2. **근본 (핫픽스)**: `rename_page` atomic tool 도입 — backlinks 자동 마이그 + LLM 단일 호출로 단순화
3. **원칙 정착 (ADR-0016)**: rename_page는 backlinks 인덱스 신뢰. 부정합 회복은 Lint(v0.5+) 담당. wiki 전체 grep 같은 O(N) fallback 안 함 → 위키 성장 시 비용 폭발 방지.

> **운영 원칙 명문화 (Kirin)**: "메타를 믿고 행동하도록 하고, 미싱되는 부분은 Lint로 처리. Lint는 비용이 비싸도 된다." → [ADR-0016](../decisions/0016-index-trust-lint-repair.md)

## 핵심 통찰

1. **agentic 흐름이 위키 본질("축적 + 진화")에 잘 맞음** — 8 patch_page : 1 write_page : 6 read_page 같은 패턴은 기존 페이지 활용을 우선시. v0.3 정적 Plan 모델에서는 어려웠던 동작.
2. **운영 부정합 vs 작업 단계 부담의 균형**: 인덱스 신뢰 + Lint 정리가 가장 깨끗한 분리. Tools가 모든 부정합 보호하려 하면 비용 폭발 + 책임 모호.
3. **prompt caching 효과 크면서도 1-iteration lag 존재** — 동적 cache_control 추가는 v0.4.1+ 검토.
4. **tier 1 한도가 운영 변수**: tier upgrade가 가장 깔끔한 mitigation. 자동 누적 또는 sales 컨택.
