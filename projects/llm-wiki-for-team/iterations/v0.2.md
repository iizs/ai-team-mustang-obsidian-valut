## 회고

### 잘 된 점

- **사전 합동 검토(Breda+Hawkeye)가 큰 가치**: v0.1에서는 Breda 1차 검토 → Hawkeye SC만 했는데, v0.2는 둘이 동시에 SPEC 검토하면서 모호한 항목 16건을 공유/합의로 흡수하고 Kirin 결정 4건만 에스컬레이션. 핑퐁 줄어 효율 큼.
- **시간 추정 범위 적중**: Realistic 60-75분 추정 → 실제 wall-clock ~60분.
- **Breda 사전 메모(race, /api/auth/config, blob 패턴 등)**가 구현 시 그대로 흡수 — 사전 검토와 구현의 정합성 높음.
- **문서 구조 분리 효과 즉시 확인**: SPEC 단일 파일 시절에는 SC 번호가 깨지면서 쌓였는데, success-criteria.md 분리 후 SC-37~40 자연스럽게 끝에 추가. iterations/v0.2.md에 결정/메모를 따로 두니 SC 본문이 깔끔하게 유지됨.

### 개선할 점

- **DB 마이그레이션 누락**: User 모델에 `created_at` 컬럼 추가됐는데 SQLAlchemy `create_all`만 쓰는 구조라 기존 DB 스키마는 v0.1 그대로 남음 → Kirin 실사용 시 로그인 흐름 깨짐. v0.3 백로그로 alembic 또는 inspect→ALTER 자동화 필요.
- **schema 변경에 대한 SC 누락**: 새 컬럼 추가 자체가 운영 환경에 영향을 주는데 SC가 새 설치(clean DB)만 가정. "기존 DB 업그레이드" 시나리오 SC 부재.
- **Race condition Advisory 1건**: 마지막 Admin 보호 — SQLite 직렬화로 사실상 보호되나 명시적 lock 강화 권장 (Hawkeye, Breda 모두 사전에 인지). v0.3+에서 처리.
