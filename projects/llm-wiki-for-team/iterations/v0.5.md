# v0.5 — Lint Issue Tracking System

## 기간 / 상태

2026-05-18 ~ 2026-05-18 / **Done**

## 목표

Sheska 자체 lint finding 추적 시스템을 구축한다. **finding 검출 + 추적 + 사용자 결정**의 인프라를 만든다. **실제 검출(Scanner) 및 정리(Tier 3 실행)는 v0.5.1+로 미룸**.

v0.5 동안 시스템에 들어오는 finding은 **사용자 신고만**. 그러나 인프라는 모든 source/category/tier를 수용하도록 설계.

## 스코프

**포함:**
- **Lint Tier Model framework** ([ADR-0017](../decisions/0017-lint-tier-model.md))
- **Lint Finding Tracker** ([ADR-0018](../decisions/0018-lint-finding-tracker.md))
  - `lint_findings` 데이터 모델
  - 사용자 신고 API + UI
  - finding 목록/조회 API + UI (`/lint` 페이지)
  - 처리 API (status ack/won't fix + reason) + UI
  - Audit trail (decided_by/at, audit-only — DELETE 미지원)

**제외 (v0.5.1+):**
- Tier 1 Scanner (자동 검출 — dangling_link, orphan, frontmatter_missing 등)
- Tier 2 Scanner (LLM judgment — stale, duplicate, quality_low 등)
- Tier 3 실행 (acknowledged → resolved, Lint Agent + Plan Review UI)
- 페이지 인라인 finding 표시 (Wiki UI 정돈 시 같이 검토)
- 외부 통합 (GitHub Issues 등 — self-hosted 약속과 충돌로 폐기)
- dedup / severity / revive / 다중 코멘트 (거대화 회피)
- 자동 트리거 / 스케줄
- 정책 관리 UI

## 변경/결정

ADR-0017 Lint Tier Model:
- 3-tier 분류: Mechanical (Tier 1) / Judgment (Tier 2) / Confirmation (Tier 3)
- v0.5는 framework + tracker 인프라만, scanner/agent는 v0.5.1+
- 카테고리별 reviewer는 코드 상수 (UI 정책 관리는 v0.6+)

ADR-0018 Lint Finding Tracker:
- 데이터 모델 단순화 — dedup/severity/revive/다중 코멘트 모두 제외
- Status: open → acknowledged | wont_fix (resolved는 v0.5.1+)
- DELETE 미지원 (audit trail)
- GitHub 통합 폐기 (self-hosted 약속 + 계정 의존성)
- v0.5 active source = `user:web` 만

신규 SC (Hawkeye 작성 예정, SC-81~):
- finding 생성 (사용자 신고)
- 목록/조회 + 필터
- 상태 변경 (ack/won't fix + reason)
- audit trail (decided_by/at)
- 권한 (인증 사용자 모두 신고 가능; 처리는 admin만? — Hawkeye 검토 시 명시)
- enum 검증 (잘못된 category/status 거부)

## 회고

### 결과 요약

- **Sheska 자체 lint finding 추적 인프라 도입 완료** — 데이터 모델 + 4 endpoint + UI(`/lint` + 신고 modal) + nav 진입점.
- Backend/Frontend 통합 17건 + 회귀 149건 = **166/166 PASS**.
- Blocking 이슈 없음, 1차 검증 PASS로 종료.
- 사람 결정 라운드 **1회**로 끝남 (PATCH 권한 / category dropdown 기본값) — Kirin이 "자율 진행 권한" 부여, 셋(Roy/Breda/Hawkeye)이 정렬되어 별도 에스컬레이션 없이 진행.

### 무엇이 잘 됐나

1. **스코프 축소가 결정적이었다.** 처음 4영역(A/B/C/D) → 3-tier framework → "lint 추적 인프라만" 으로 단계적으로 좁히며 v0.5에 끝낼 수 있는 단위가 됐다. Kirin이 "이번엔 이것만" 가이드를 강하게 잡아준 효과.
2. **거대화 회피 원칙 (ADR-0018)** — dedup / severity / revive / 다중 코멘트 / assignee / label/milestone 전부 의도적 제외. 풀스택 issue tracker 흉내를 피해 v0.5에 끝낼 수 있었다.
3. **GitHub 통합 거절 결정 (ADR-0018)** — self-hosted 약속과 충돌 + 계정 의존성. 트레이드오프 명시 후 결정.
4. **Framework + Tracker 분리 (ADR-0017 / ADR-0018)** — Tier 분류 framework는 정의하되 실제 Scanner/Agent는 v0.5.1+로 미룸. 단계 도입 경로가 명확해졌다.
5. **권한 default 셋 정렬** — Breda Q1/Q2 "권장" default = Hawkeye가 작성한 SC의 default. 두 권장이 일치해 Kirin 결정 라운드 절약.

### 무엇이 어려웠나 / 개선점

1. **SC-81 본문과 ADR-0018 데이터 모델 표현 충돌** — Hawkeye SC 작성 시 `page_path` 필수로 표현했으나 ADR 본문은 nullable 명시. 검증 단계에서 Hawkeye가 SC 본문 정정으로 해결. **교훈**: SC 작성 시 ADR 데이터 모델 본문을 칸 단위로 비교 (v0.4 SC-54/58 동일 패턴 반복).
2. **`acknowledged` 받아가는 주체 없음** — ADR-0018 트레이드오프로 명시한 부분. v0.5에서 사용자가 "고친다"는 행위가 안 일어남. v0.5.1까지 한 phase 기다림. Framework 정착 우선.
3. **dedup 부재의 운영 영향 미지** — 같은 이슈 반복 신고 시 finding 매번 신규 생성. v0.5.x dedup_key 도입 여부는 운영 관찰 후 결정.
4. **자동 진행 패턴의 한계** — v0.5는 인프라성 phase + 결정 라운드가 권장 default로 수렴 가능했기에 자율 진행이 통했다. 더 큰 결정이 필요한 phase에선 신중 권장 (Hawkeye Advisory C).
