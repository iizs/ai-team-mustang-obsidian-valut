## 회고

### 잘 된 점

- **단일 job + 다중 액션 구조의 자연스러운 확장**: Phase A의 plan 인프라가 그대로 Phase B로 확장됨 — 코드 변경 최소. Sub-job 모델 도입 검토했다가 보류한 결정이 맞았음.
- **Hawkeye SC 통합 정합성**: SC-52~63 인벤토리 11/1 (Blocking/Advisory)이 코드 구현과 깔끔하게 1:1 매핑. v0.3 때 학습한 "frontmatter 정책 명시" 같은 디테일이 v0.3.1 SC-52에서 사전에 잡힘.
- **작업 시간 추정 적중 (코드 작업 기준)**: realistic 65-80분 → 실제 wall-clock ~70분 (Discord 타임스탬프 elapsed는 ~12분, "wall-clock"의 의미는 v0.4부터 명확화 예정).
- **빈 plan을 SUCCESS로 처리하는 결정**: Breda는 FAILED 권장했지만 Hawkeye가 SC-59에 SUCCESS + log 권장 → 토론 후 후자 채택. 운영 환경에서 LLM이 "할 일 없음"이라 판단하는 케이스를 정상 동작으로 인정하는 게 자연스러움.
- **Plan 가시성**: `Job.payload`에 plan 전체 보존 + Jobs UI에서 액션별 outcome 표시 — 사용자가 "왜 어떤 액션은 skip됐나" 추적 가능.

### 개선할 점

- **Advisory 2건 (SPEC vs 구현 표현 차이)**:
  - SC-54 `git rm` 표현: 구현은 `unlink + index.remove`. 결과 동등하지만 SC가 구현 세부에 너무 깊이 갔던 case. 마감 시 표현 완화로 흡수.
  - SC-58 graceful degrade: SPEC은 "INGEST와 동일"이라 적었는데 실제는 WIKI_COMMAND가 우리 prompt 통제라 legacy fallback 의미 없음. SC 본문에서 "즉시 FAILED"로 명시 변경.
  - 교훈: SC 작성 시 "구현 방식"보다 "검증 가능한 결과"에 초점. 그리고 컨텍스트가 다른 두 흐름을 단순히 "동일하다"고 적으면 후속 오류 부르기 쉬움.
- **`merge_into` 옵션 (a) 채택의 한계 — 검증 필요**: Plan 출력 그대로 적용은 LLM이 기존 페이지 내용을 모르고 통합본 작성한 거라 통합 품질이 낮을 가능성. 실측 후 옵션 (b) 재호출 보강으로 진화 검토 필요. (v0.4에서 agentic 재설계 들어가면 이 결정 자체가 재논의 대상.)
- **사용자 승인 절차 부재**: WIKI_COMMAND는 즉시 실행 → LLM이 자연어 의도를 잘못 해석하면 즉시 다중 페이지 손상. 운영 초기엔 log.md / Jobs 탭 plan_summary가 유일한 안전망. **v0.4 agentic 재설계 논의에서 다시 다뤄질 핵심 주제**.
