## 브레인스토밍 메모 (2026-04-19)

### 배경 / 문제의식

AI를 팀에 도입하면서 생긴 새로운 숙제:
> **사람 간의 암묵적 소통을 텍스트로 만들어야 AI가 따라올 수 있다.**

기존에는 대화로 해결하던 것들이, AI 도입 이후엔 모두 텍스트 산출물로 남겨야 함.
→ 기획자·디자이너에게 GitHub 사용 교육 중 (에이전트가 읽을 수 있는 공유 저장소 확보 목적)

### 현재 팀의 공유 레이어

| 도구 | 역할 |
|------|------|
| **두레이** | 태스크 관리 (GitHub Issues 역할, API 있음 → 스킬로 연동 가능) |
| **GitHub** | 산출물 관리 (코드, 문서) |
| **메시지 채널 (Discord)** | 흐름 + 의사결정 공간 (고민 중인 레이어) |

### 통합 채널의 역할

1. **교차점 의사결정** — 기획/디자인/개발이 서로 영향을 주는 결정을 함께 보는 공간
2. **매니저 가시성** — 대화에 끼지 않아도 전체 업무 흐름 파악 가능 (채팅형 대시보드)
3. ~~에이전트 간 직접 협력~~ — 현 시점엔 핵심 아님, 보류

### 핵심 인사이트

> **각 팀원이 자신의 로컬 에이전트를 메시지 채널에 참여시킬 수 있다.**

- 기획자는 기획 에이전트, 디자이너는 디자인 에이전트, 개발자는 개발 에이전트를 같은 채널에 연결
- 에이전트가 별도 리모트 서버 없이 각자 로컬에서 Discord에 붙으면 됨
- 채널 대화 자체가 에이전트들의 공유 컨텍스트(메모리)가 됨
- 미팅에 노트북 들고 들어가듯, 자신의 에이전트를 데리고 들어가는 방식

온보딩 흐름:
> Discord 봇 토큰 발급 → Claude Code Discord 플러그인 설정 → 채널 초대

### 미결 허들

- **Discord 채널 기능이 실험적(비공식) 기능**임 → 안정성/지속성 불확실
- **Claude Code 외 에이전트가 필요한 직군 존재** — 디자인처럼 다른 AI 도구를 쓰는 경우, 동일 구조 적용 어려움

### 다음 탐색 방향
- 디자인 직군을 위한 대안 에이전트 연동 방식
- Discord 외 메시지 채널 후보 (Slack 등)
- 두레이 스킬 연동 구체화

## 브레인스토밍 메모 (2026-05-01) — 산출물과 지식 정보의 구분

### 배경 확장
- 논의 대상: 온라인 모바일/웹 서비스를 운영하는 조직 전체 (CTO 관점)
- 궁극적 목표: 조직 전체에서 사람+에이전트가 함께 일하는 환경 설계

### 산출물(Artifact) 계층

최종 산출물은 "서비스(서비스 동작 그 자체)"이며, 이에 도달하기 위한 산출물들:

```
Source Code → [서비스]
  ↑
기술 스펙 / API Reference
  ↑
서비스 동작 상세 / 정책 문서
  ↑
UI/디자인 문서
  ↑
UX 정의 문서
  ↑
상위 기획서 / PRD
```

**현재 저장 위치**: 개인 디바이스, 메일함, 두레이, GitHub(소스코드만) 등 분산

### 핵심 발견: 정보의 두 가지 성격

| 구분 | 성격 | 예시 | 관리 방식 |
|------|------|------|----------|
| **프로젝트 정보** | 생명주기 한정적 | PRD, 회의록, 기획서, 디자인 시안 | 기존 위치(두레이, 메일 등)에서 AI가 필요 시 읽어옴 |
| **서비스 지식 베이스** | 서비스가 살아있는 동안 지속 | 서비스 철학, 핵심 용어, 반복 정책, 도메인 규칙 | **한 곳에 모아 AI가 항상 참조 가능하게** |

**사람끼리 일할 때**: 흩어진 문서가 큰 이슈 아님 (물어보면 됨, 맥락이 사람 머릿속에)  
**AI가 끼면**: AI는 물어볼 수도, 머릿속 맥락 참조도 불가 → 접근 가능한 텍스트 필요

### Obsidian의 역할
- **프로젝트 문서** → Obsidian 불필요, 기존 도구에서 AI가 읽어오면 됨
- **서비스 지식 베이스** → Obsidian이 적합 (지속적, 구조화된, AI 접근 가능한 저장소)
  - 에이전트가 매번 "이 서비스가 뭔지" 설명받지 않아도 되도록
  - 우리 팀의 CONSTITUTION.md / WORKFLOW.md 와 같은 개념을 서비스 단위로 적용

### 지식 베이스와 프로젝트의 순환 구조

```
지식 베이스 v1
  ↓ (프로젝트가 v1을 참조해서 시작)
프로젝트 (기획 → 설계 → 개발 → 배포)
  ↓ (프로젝트 중 새로 결정된 것들이 지식 베이스에 반영)
지식 베이스 v2
  ↓
다음 프로젝트...
```

- 지식 베이스는 프로젝트에 의해 소비되는 동시에 업데이트되는 살아있는 문서
- 복수 프로젝트 동시 진행 시 지식 베이스 업데이트 충돌 가능 → git 충돌 해소 방식으로 처리 가능
- 우선 단일 프로젝트 흐름으로 구체화 시작

### 용어 정의

| 용어 | 설명 |
|------|------|
| **Project Artifacts** | 생명주기가 한정적인 프로젝트 산출물 (PRD, 기획서, 회의록, 디자인 시안 등) |
| **Knowledge Base (KB)** | 서비스가 살아있는 동안 지속되는 지식 저장소 (서비스 철학, 용어, 정책, 도메인 규칙 등) |

### 미결 사항
- 지식 베이스 구체적 구조 설계 (어떤 파일들로 구성할 것인가)
- 프로젝트 종료 후 지식 베이스 업데이트 프로세스 (누가, 언제, 어떻게)
- AI가 두레이/메일 등 기존 위치의 프로젝트 문서를 읽어오는 방법 구체화
- 팀 전체가 지식 베이스를 기여/유지하는 방식
